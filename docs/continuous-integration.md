# Continuous integration

P0.6 adds [CI](../.github/workflows/ci.yml) and makes the documented local
verification reproducible from a fresh checkout. The workflow runs on pull
requests, pushes to `main` and manual dispatch. It has one Ubuntu 24.04 job,
`Verify`, with a 15-minute limit.

## Workflow steps

1. **Checkout:** `actions/checkout@v7` reads the event's revision. Normal pull
   request runs test GitHub's merge revision, not an arbitrary branch selected
   by the workflow. Credentials are not persisted after checkout.
2. **Toolchain and cache:** `pnpm/setup@v3` installs native pnpm from the root
   `packageManager` declaration and Node from `.nvmrc`. This action supports
   pnpm 12 and manages its runtime; a second Node setup action is unnecessary.
   Its automatic dependency installation is explicitly disabled.
3. **Frozen installation:** `pnpm install --frozen-lockfile` always executes,
   including after a cache hit. It validates manifest/lockfile consistency and
   links a fresh dependency tree.
4. **Verification:** `pnpm verify` checks formatting, lint, application/test
   types, behavior tests with per-file 90% coverage, and production builds.
   Local and CI verification therefore share the same script and thresholds.

The job has only `contents: read` token permissions. New runs cancel older
runs for the same workflow/ref. There are no deployments, provider credentials
or external application messages. Required-merge-check settings are separate
repository configuration; this workflow reports its result without modifying
those settings.

## Cache is an optimization, not an installation gate

The setup action caches pnpm's content-addressable store, keyed by the root
`pnpm-lock.yaml`. It does not cache `node_modules`, `dist`, env files or
conversation data. A miss downloads needed packages; a hit reuses stored
package content. Both cases execute the same frozen-install and verification
steps. Do not add `if: cache-hit != 'true'` to the install step.

The lockfile remains committed and is never regenerated by CI. Package changes
must update it locally and pass a frozen installation before review.

## CI and local environment

CI sets only the public build setting `VITE_API_BASE_URL=/api`. The build
therefore needs no private `.env`. This is a same-origin deployment URL,
not an automatically configured Vite development proxy. Backend tests supply
their own validated settings, temporary files and local listeners; compiling
the backend does not start it or load dotenv.

For local development, use the root README's env examples. The backend needs
all four platform variables. The frontend example uses an absolute localhost
API URL so the two development servers can communicate. Backend startup loads
dotenv from the process working directory, normally `backend/` when invoked
through its package scripts. Process values take precedence over env-file
values. Frontend env changes require a Vite restart or a production rebuild.

The API has no `/health` or `/healthz` route yet. The documented manual check
uses `/api/chats/list`, which exercises the HTTP handler but is not a model,
readiness or durable-storage guarantee. A 503 from generation means the model
is deliberately unconfigured, not that the server failed to start.

## Validation and limits

Local validation uses a fresh clone of the committed source with the P0.6
patch applied. It starts with no env files, dependency tree or build output.
The README's example copies and frozen installation are then followed by
`pnpm verify`. A second invocation uses the CI public URL without env files.
The already selected Node/pnpm versions are checked against `.nvmrc` and
`packageManager`; installing those tools globally is not repeated.

The frozen-install failure path is checked by changing a dependency specifier
in the disposable clone while keeping its lockfile unchanged. Even with the
local store populated, installation must fail; the original manifest is then
restored. Workflow syntax is checked separately with actionlint.

A local run is evidence of the commands, not a claim that a hosted GitHub job
has run. The first hosted run remains pending until this workflow is committed
and pushed or included in a pull request. CI setup does not push automatically.
The existing bundle-size warning stays visible and is documented in
[quality gates](quality-gates.md).
